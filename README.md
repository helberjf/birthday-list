# Birthday List — Digital Invitations and RSVP

A customizable party invitation application with RSVP, themes, photos and an administrative workspace. Guests open the invitation and respond; the organizer manages event content, attendance and follow-up information.

[API contract](lib/api-spec/openapi.yaml) · [Backend](artifacts/api-server/src) · [Frontend](artifacts/birthday-invite)

## Architecture

The pnpm monorepo combines React/Vite/Tailwind, Express 5, Zod validation and a React Query client generated by Orval from OpenAPI. A shared data-store interface supports PostgreSQL/Drizzle, Firestore, Turso/libSQL and local memory modes.

The repository implements invitation and attendance workflows. It should not be presented as a payment-processing product merely because invitations may be sold commercially.

## Recommended local path: PostgreSQL

Requirements: **Node.js 22–24, pnpm 9+ and Docker**.

```bash
pnpm install
cp .env.example .env.local
```

In PowerShell, use `Copy-Item .env.example .env.local` instead of `cp`. Before starting the database or pushing the schema, configure matching `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` values, plus an explicit `ADMIN_PASSWORD` and `JWT_SECRET`. For the API and Drizzle commands running on the host, `DATABASE_URL` must use `127.0.0.1` and the published PostgreSQL port; `postgres` is the Compose-internal hostname, not the host address. Replace the example connection credentials with the same values configured for Compose.

```bash
docker compose --env-file .env.local up -d postgres
pnpm --filter @workspace/db run push
```

Then start the API and frontend in separate terminals:

```bash
pnpm run dev:api
pnpm run dev:web
```

The UI is at `http://localhost:5173`, administration at `/admin` and the API at `http://localhost:3000/api`. The schema-push command changes the selected development database.

Alternatively, `bash dev.sh` or `.\dev.ps1` checks prerequisites, prepares environment configuration, installs dependencies, starts PostgreSQL, applies the schema and launches both applications. Their reset options recreate local database state; use them only for a disposable lab.

## Persistence modes

| Mode | Selection and use | Important boundary |
| --- | --- | --- |
| PostgreSQL | Set `DATABASE_PROVIDER=postgres` and `DATABASE_URL`; recommended local evaluation path. | Requires a running database and schema setup. |
| Firestore | Set `DATABASE_PROVIDER=firebase`; configure `FIREBASE_PROJECT_ID`, `FIREBASE_DATABASE_ID` and private service-account configuration. | Provider-specific data access is implemented in the REST adapter; it is not identical to SQL behavior. |
| Turso/libSQL | Set the provider or a `libsql://` database URL; inspect the [adapter](artifacts/api-server/src/lib/turso-store.ts) for its configuration. | Different persistence and concurrency behavior must be checked independently. |
| Memory | Local development fallback when no provider or database URL is configured. | Data is disposable; this mode is explicitly rejected on Vercel. |

[Provider selection](artifacts/api-server/src/lib/data-store.ts) is authoritative. A PostgreSQL URL selects PostgreSQL automatically; the application does not silently provide durable storage when configuration is missing.

## API and generated client

Core endpoints include event configuration, themes, RSVP creation, guest listings, statistics, gallery photos and administrative theme management. [Guest routes](artifacts/api-server/src/routes/guests.ts) return a reduced public view and an expanded administrator view; decide which guest details should be public before a real event.

When changing the API contract, update [openapi.yaml](lib/api-spec/openapi.yaml), run the generator and review both server validation and client changes:

```bash
pnpm --filter @workspace/api-spec run codegen
pnpm run typecheck
pnpm run build
```

## Architecture trade-offs

These rows analyze the current design and its operational implications.

| Choice | Benefit | Cost or boundary |
| --- | --- | --- |
| Generated client and validation contracts | Reduces manually duplicated request/response shapes. | Contract changes require regeneration and coordinated server/client review. |
| Multiple persistence adapters | Gives deployment flexibility and a lightweight local demo. | Increases the behavior matrix; duplicates, pagination and concurrent updates need provider-specific checks. |
| React SPA plus Express API | Separates the interactive invitation from backend rules. | Hosting must route API requests and frontend paths correctly. |
| Public RSVP/guest views with administrator-only detail | Supports a social invitation experience while restricting operational fields. | Public visibility is a product/privacy decision, not simply a UI setting. |
| In-process scheduled reminders | Straightforward on a persistent server. | Serverless requests do not guarantee a continuously running scheduler; reminders need an explicit scheduled invocation strategy there. |

## Deployment and verification

[vercel.json](vercel.json) uses `build:vercel`, serves the frontend build and rewrites API requests to its function. Configure a persistent provider, `JWT_SECRET`, `ADMIN_PASSWORD` and `ALLOWED_ORIGINS`; Firestore settings are illustrated by [.env.firebase.example](.env.firebase.example). Keep service-account material on the server.

For a VPS, copy [.env.vps.example](.env.vps.example) to `.env`, configure matching database and application values, then use `docker compose up -d --build`. Compose reads `.env` automatically; if you choose another file, provide it with `--env-file`. The container applies the Drizzle schema on startup; review that behavior for deployed data and put HTTPS in front of the service.

The [CI workflow](.github/workflows/ci.yml) installs dependencies and runs type checking/build. There is no root application-test command. Add provider-contract and RSVP authorization tests before interpreting a successful build as workflow validation. Browser behavior, real email/WhatsApp delivery and persistence integrations require separate evidence.
